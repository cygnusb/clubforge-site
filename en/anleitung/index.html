Installation guide

Step by step from a rented server to a running club server with a certificate, backups, and the first admin. Some technical experience (SSH, setting DNS records) is enough; the installation itself takes a few minutes.

Prepare · DNS · Get the installer · Install · Hetzner with OpenTofu · Backup key · Sign in · After that · Troubleshooting

Two routes: on a server you already rent, you install over SSH (steps 2 to 4). On Hetzner Cloud, an OpenTofu template can create the server, firewall, and DNS for you instead. Both continue with step 5. The setup assistant puts together the commands with your details.

The examples use the names app., sync., and login.your-club.example. Use your own names everywhere. What you need in terms of server, domain, and services, and what it costs, is on the Operations page.

1. Prepare

A fresh server with Debian 12/13 or Ubuntu 24.04 (x86_64 or arm64), at least 2 vCPUs, 4 GB of RAM, and a 40 GB disk, with a fixed IPv4 address and located in the EU. At Hetzner, a CAX11 or CX22 is enough. Sign the data processing agreement in your provider's console.

Decide within the club beforehand:

  • The three names. They cannot be changed after the installation without setting up sign-in again (all logins would be lost, the club data would not).
  • Who looks after the server (SSH access) and who holds the backup key: two people, through a shared password manager.
  • The club brand: name, a logo as SVG or PNG at an https address, two or three colors (#rrggbb), and optionally your own word for groups. All of it can be changed in the app later.
  • The version. For running a club, pick a fixed version, currently 0.4.0. What changes with each version is under Versions.

2. Set the DNS records

In your club's domain, set three A records, all pointing at the server's IPv4 address, with a TTL of 300 while you set things up:

Name (type A)Serves
app.your-club.exampleweb app and API
sync.your-club.examplesync
login.your-club.examplesign-in

Check from your own computer; every line must show the server's IP (new records take a few minutes, rarely up to an hour):

dig +short app.your-club.example
dig +short sync.your-club.example
dig +short login.your-club.example
  • Don't set an AAAA record unless you are sure. Let's Encrypt prefers IPv6; if the record points nowhere, you get no certificate. Everything works over IPv4.
  • If your domain has a CAA record, it must allow Let's Encrypt (0 issue "letsencrypt.org").
  • Behind a proxy or CDN (such as Cloudflare with the orange cloud), the certificate won't work: set the records to “DNS only”.

3. Get and check the installer

Log in to the server over SSH. The installation script is on this website. Download and check it first, then run it; no blind curl | bash:

curl -fsSLO https://cygnusb.github.io/clubforge-site/install.sh
curl -fsSL  https://cygnusb.github.io/clubforge-site/install.sh.sha256
sha256sum install.sh     # must match the checksum shown
less install.sh          # if you like: read it, it's a shell script

The checksum catches transfer errors but doesn't protect against a tampered website. For more assurance, read the script or compare with the checksum attached to the release. The server builds nothing and needs no Git: the installer pulls a ready-made image (docker.io/cygnusbn/clubforge, or ghcr.io/cygnusb/clubforge).

4. Install

One command sets everything up, including the club brand and the first admin. Add --dry-run to see only what it would do:

sudo bash install.sh \
  --app app.your-club.example \
  --sync sync.your-club.example \
  --login login.your-club.example \
  --email board@your-club.example \
  --club "Your Club" --version 0.4.0 \
  --logo https://your-club.example/logo-white.svg \
  --logo-light https://your-club.example/logo-dark.svg \
  --primary '#117733' --dark '#0a2a14' --accent '#88ccaa' \
  --admin-first Vera --admin-last Board

With no further options, sudo bash install.sh asks for everything step by step in the terminal and at the end shows the same call without questions, for you to keep.

What the installer does, each step only if it isn't done yet (running it twice is safe):

  1. Checks the system, memory, and DNS.
  2. Installs Docker from the official repository and sets up log rotation.
  3. Sets up the firewall: incoming only 22, 80, and 443.
  4. Turns on automatic security updates.
  5. Creates the user clubforge, pulls the image, and unpacks the operations files to /opt/clubforge/deploy.
  6. Writes the settings with random secrets (/opt/clubforge/deploy/.env) and a key for the backups.
  7. Sets up the daily backup (03:15).
  8. Starts everything and checks the result. The first start takes a few minutes, mostly for sign-in and the certificate.

More options, all optional: --favicon, your own word for groups (--group-one Team --group-other Teams --group-gender n), mail (--smtp-host, --smtp-port, --smtp-user, --smtp-security, --smtp-from; the password in the environment variable CF_SMTP_PASSWORD), a backup key you created yourself (--age-recipient, see below), and storage for attachments (--s3-*, see After that). bash install.sh --help lists them all.

The .env holds all of the server's secrets. It is part of every backup; never pass it on, never commit it.

Or: Hetzner Cloud with OpenTofu

Instead of doing steps 2 to 4 by hand, an OpenTofu template creates everything at Hetzner in one go: server, firewall (22, 80, 443), fixed IPv4 and IPv6 addresses, and optionally the DNS records. The server installs itself on first boot, with the club brand and the first admin. Tried on a CAX11: about 2.5 minutes from tofu apply to a green check. On your own computer you need a terminal, an SSH key (ssh-keygen -t ed25519), OpenTofu, and Docker to get the template out of the image.

Account, project, API token

  1. Create an account at console.hetzner.cloud and a separate project for clubforge. Object Storage for backup copies is best kept in a second project later.
  2. In the project, under Security › API tokens, create a token with read and write access. It is shown only once.
  3. Sign the data processing agreement in the console.
export TF_VAR_hcloud_token='…'     # in the terminal only, never in a file

Get and fill in the template

cid=$(docker create docker.io/cygnusbn/clubforge:0.4.0)
docker cp "$cid:/opt/clubforge/deploy/cloud" ./clubforge-cloud && docker rm "$cid"
cd clubforge-cloud/hetzner
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars

A filled-in example:

app_host          = "app.your-club.example"
sync_host         = "sync.your-club.example"
login_host        = "login.your-club.example"
admin_email       = "board@your-club.example"
club_name         = "Your Club"
ssh_public_key    = "ssh-ed25519 AAAA… name@computer"
ssh_allowed_cidrs = ["203.0.113.7/32"]       # only your address may use SSH
clubforge_version = "0.4.0"
# server_type = "cax11"   location = "fsn1"   dns_zone = "your-club.example"
# age_recipient = "age1…"  (a backup key you created yourself, see step 5)

logo          = "https://your-club.example/logo-white.svg"
logo_light    = "https://your-club.example/logo-dark.svg"
color_primary = "#117733"
color_dark    = "#0a2a14"
color_accent  = "#88ccaa"
admin_first   = "Vera"
admin_last    = "Board"

Without ssh_allowed_cidrs, SSH is open to the whole internet. The default is a CAX11 (arm64) in Falkenstein; server_type = "cx22" picks Intel, and location can also be nbg1 or hel1. Optional: server_backups = true (images of the whole server by Hetzner, +20 %; no substitute for the encrypted backup) and volume_size_gb for an extra volume.

Fixed IP first, then DNS

So that the names already resolve on first boot, the IP is created first:

tofu init
tofu apply -target=hcloud_primary_ip.v4
tofu output ipv4

Point the three A records at this IP as in step 2 and check them with dig. If the domain is in Hetzner DNS in the same project, set dns_zone instead; the next step then creates the records itself.

Create the server

tofu plan                                 # read it carefully: server, firewall, IPs
tofu apply
$(tofu output -raw installationsprotokoll)   # follow the progress

The server downloads install.sh from this website, checks the checksum, pulls the image, and sets everything up. The check.sh report is at the end of the log. If the installation stops because of DNS: fix the records and run sudo /root/clubforge-install.sh on the server again.

Collect the credentials

ssh root@<ipv4> cat /root/clubforge-erste-anmeldung.txt   # the first admin's one-time password
ssh root@<ipv4> cat /root/clubforge-backup-key.txt        # without age_recipient: into the password manager
ssh root@<ipv4> rm /root/clubforge-erste-anmeldung.txt /root/clubforge-backup-key.txt

tofu output naechste_schritte sums this up (in German). Continue with step 5 and step 6. A later tofu apply doesn't rebuild the running server; after that, you change settings in the .env on the server. tofu destroy removes the template's server, IPs, firewall, volume, and DNS records; save the backups first.

5. Secure the backup key

Backups are encrypted. The server only knows the public key; it can write backups but not read them. You need the secret key (AGE-SECRET-KEY-1…) to restore a backup. Without it, every backup is worthless.

  • Interactively, the installer shows it once. Put it in the club's password manager (two people), then confirm.
  • Unattended (--yes, cloud-init), it is in /root/clubforge-backup-key.txt: copy it, put it in the password manager, delete the file. check.sh reminds you as long as it is there.
  • Cleanest: create it yourself and pass only the public part. Then no key file is ever created on the server.
# on your own computer
age-keygen -o key.txt            # shows "Public key: age1…"; key.txt goes into the password manager
sudo bash install.sh … --age-recipient age1…

6. Sign in and check

With --admin-first and --admin-last, the first admin already exists. Their one-time password is at the end of the output, or in /root/clubforge-erste-anmeldung.txt when run unattended (delete it after passing it on). Without these options, create the admin now:

sudo -u clubforge /opt/clubforge/deploy/admin.sh board@your-club.example Vera Board
  1. Open https://app.your-club.example: the club's name, colors, and logo are already there.
  2. Sign in with the email address and the one-time password; sign-in asks for a new password right away.
  3. This person is a club admin and sets up everything else in the web app under Profile › Admin: groups, features, terms, brand, code of conduct, privacy and imprint, member source (easyVerein or CSV).

One command checks the server's state at any time. You want OK for services, DNS, certificate, endpoints, backup, and disk:

sudo -u clubforge /opt/clubforge/deploy/check.sh

7. After that

Backups and restore test

The backup runs daily, encrypted, kept for 30 days, in /var/backups/clubforge/. A backup on the same server doesn't protect against losing that server: with BACKUP_S3_* in the .env, each one is also copied to S3 storage, ideally in a different project from the server. Restore once right after the installation and then every quarter, into a throwaway container, without touching the running system:

cd /opt/clubforge/deploy
sudo -u clubforge ./backup.sh                      # a backup right now
install -m 600 /dev/null /dev/shm/age-key.txt && nano /dev/shm/age-key.txt   # key from the password manager
./restore.sh --identity /dev/shm/age-key.txt --verify
shred -u /dev/shm/age-key.txt

The script reports that the restore test passed (in German, “Restore-Test bestanden”), with counts for members, events, and messages.

Updates

System security updates run on their own; if /var/run/reboot-required exists, reboot at a quiet moment. One command installs a new clubforge version: backup, new image, database update, check. With --announce, members see the maintenance in the app beforehand.

cd /opt/clubforge/deploy
sudo -u clubforge ./update.sh --version 0.4.0 --announce 10m

Notes for each version are under Versions.

Mail

Without SMTP access the server sends no mail; the app and push work anyway. Put CF_SMTP_HOST, CF_SMTP_PORT, CF_SMTP_USER, CF_SMTP_PASSWORD, CF_SMTP_SECURITY (starttls or ssl), and CF_MAIL_FROM in the .env, then run docker compose up -d api worker in /opt/clubforge/deploy. Use port 587: many cloud providers block port 25 (sometimes 465 too), and Hetzner blocks both for new accounts.

Attachments (optional)

Photos, files, and GPX routes need a private bucket of their own at an S3 provider, such as Hetzner Object Storage, separate from the backups. Without it everything runs, just without attachments.

# in /opt/clubforge/deploy/.env
CF_S3_ENDPOINT=https://fsn1.your-objectstorage.com
CF_S3_REGION=fsn1
CF_S3_BUCKET=your-club-attachments
CF_S3_ACCESS_KEY=…
CF_S3_SECRET_KEY=…
cd /opt/clubforge/deploy
docker compose up -d --force-recreate api worker
sudo -u clubforge ./check.sh                       # section on attachments

Maps (optional)

The map tiles for your region live on your own server. One command downloads them and turns maps on; --dry-run only shows the size. Baden-Württemberg (bw) needs about 1 GB, Germany (de) about 7.4 GB, with the Alps (de-alpen) about 9.9 GB; with --maxzoom 14, a little over half that.

cd /opt/clubforge/deploy
./maps.sh --region bw --dry-run
./maps.sh --region bw

Search by meaning (optional)

Search then also finds paraphrases, for example “annual meeting” finds the general assembly. A small language model computes this on your own server; no text goes to third parties. The command downloads the model (about 130 MB) and turns the service on; while it catches up on existing content it needs about 550 MB of memory. check.sh shows the progress, and it can be turned off under Admin › Search.

cd /opt/clubforge/deploy
./embeddings.sh

Monitoring

An external service (Uptime Kuma, healthchecks.io, or similar) calls https://app.your-club.example/api/v1/readyz every five minutes and emails two people when it fails. With BACKUP_HEARTBEAT_URL in the .env, every successful backup checks in there; if it stops, you get an alert.

8. Troubleshooting

Always start with check.sh; for anything red, look at the service's log: docker compose logs --tail=100 <service> in /opt/clubforge/deploy.

SymptomFix
Installer says DNS is wrongCheck the records with dig, wait, run the installer again; it picks up where it stopped.
Certificate error in the browserPorts 80 and 443 must also be open in the provider's firewall (curl -I http://app.your-club.example must return 308). Check the AAAA record and any proxy. After many failed attempts, Let's Encrypt blocks for about an hour.
Services get killed (“Killed”)Less than 4 GB of RAM: pick a bigger server.
“Image … not available”Check the version; use --image ghcr.io/cygnusb/clubforge for the other registry.
Sign-in: no active member with this addressRun admin.sh (or admin.sh --member) with the same address.
Forgotten passwordSet a new one in the sign-in admin console (https://login.your-club.example/ui/console, user zitadel-admin, password ZITADEL_ADMIN_PASSWORD from the .env).

Other routes lead to the same result: cloud-init (the server sets itself up on first boot, with any provider) and OpenTofu templates like the Hetzner one for AWS and Google Cloud too. Both are in the image, under /opt/clubforge/deploy/cloud/ and /opt/clubforge/deploy/cloud-init.yaml; docker create docker.io/cygnusbn/clubforge:0.4.0 with docker cp gets them onto your own computer.
