Installations­anleitung

Schritt für Schritt vom gemieteten Server zum laufenden Vereinsserver mit Zertifikat, Backup und erster Admin-Person. Etwas Technik-Erfahrung (SSH, DNS-Einträge setzen) genügt; die Installation selbst dauert wenige Minuten.

Vorbereiten · DNS · Installer laden · Installieren · Hetzner mit OpenTofu · Backup-Schlüssel · Anmelden · Danach · Wenn es hakt

Zwei Wege: Auf einem schon gemieteten Server installiert ihr per SSH (Schritte 2 bis 4). Bei Hetzner Cloud kann stattdessen eine OpenTofu-Vorlage Server, Firewall und DNS gleich mit anlegen. Danach geht es für beide mit Schritt 5 weiter. Die Befehle mit euren Angaben stellt der Einrichtungs-Assistent zusammen.

Die Beispiele nutzen die Namen app., sync. und login.mein-verein.example. Setzt überall eure eigenen Namen ein. Was ihr an Server, Domain und Diensten braucht und was es kostet, steht auf der Seite Betrieb.

1. Vorbereiten

Ein frischer Server mit Debian 12/13 oder Ubuntu 24.04 (x86_64 oder arm64), mindestens 2 vCPU, 4 GB Arbeitsspeicher und 40 GB Platte, mit fester IPv4-Adresse und Standort in der EU. Bei Hetzner reicht ein CAX11 oder CX22. Den Vertrag zur Auftragsverarbeitung schließt ihr in der Konsole des Anbieters ab.

Vorher im Verein entscheiden:

  • Die drei Namen. Ein Wechsel nach der Installation geht ohne Datenverlust, meldet aber alle Geräte ab, und installierte Apps brauchen eine Weiterleitung vom alten Namen.
  • Wer den Server betreut (SSH-Zugang) und wer den Backup-Schlüssel hat: zwei Personen, über einen gemeinsamen Passwortmanager.
  • Die Vereinsmarke: Name, Logo als SVG oder PNG unter einer https-Adresse, zwei bis drei Farben (#rrggbb) und auf Wunsch ein eigener Begriff für Gruppen. Alles lässt sich später in der App ändern.
  • Die Version. Für den Vereinsbetrieb eine feste Version wählen, aktuell 0.4.0. Was sich je Version ändert, steht unter Versionen.

2. DNS-Einträge setzen

Bei der Domain des Vereins drei A-Einträge setzen, alle auf die IPv4-Adresse des Servers, während der Einrichtung mit TTL 300:

Name (Typ A)Inhalt
app.mein-verein.exampleWeb-App und API
sync.mein-verein.exampleSynchronisation
login.mein-verein.exampleAnmeldung

Vom eigenen Rechner prüfen; jede Zeile muss die IP des Servers zeigen (neue Einträge brauchen einige Minuten, selten bis zu einer Stunde):

dig +short app.mein-verein.example
dig +short sync.mein-verein.example
dig +short login.mein-verein.example
  • Keinen AAAA-Eintrag setzen, solange ihr nicht sicher seid. Let's Encrypt prüft bevorzugt über IPv6; zeigt der Eintrag ins Leere, kommt kein Zertifikat. Alles funktioniert über IPv4.
  • Ein CAA-Eintrag auf der Domain muss Let's Encrypt erlauben (0 issue "letsencrypt.org"), falls es einen gibt.
  • Hinter einem Proxy oder CDN (etwa Cloudflare mit orangener Wolke) klappt das Zertifikat nicht: die Einträge auf „nur DNS“ stellen.

3. Installer laden und prüfen

Per SSH auf dem Server anmelden. Das Installationsskript liegt auf dieser Webseite. Erst laden und prüfen, dann ausführen, kein blindes curl | bash:

curl -fsSLO https://cygnusb.github.io/clubforge-site/install.sh
curl -fsSL  https://cygnusb.github.io/clubforge-site/install.sh.sha256
sha256sum install.sh     # muss mit der angezeigten Summe übereinstimmen
less install.sh          # wer will: lesen, es ist ein Shell-Skript

Die Prüfsumme erkennt Übertragungsfehler, schützt aber nicht vor einer manipulierten Webseite. Wer mehr Sicherheit will, liest das Skript oder vergleicht mit der Prüfsumme am Release. Der Server baut nichts und braucht kein Git: Der Installer zieht ein fertiges Image (docker.io/cygnusbn/clubforge, alternativ ghcr.io/cygnusb/clubforge).

4. Installieren

Ein Befehl richtet alles ein, gleich mit Vereinsmarke und erster Admin-Person. Mit --dry-run davor zeigt er nur, was er tun würde:

sudo bash install.sh \
  --app app.mein-verein.example \
  --sync sync.mein-verein.example \
  --login login.mein-verein.example \
  --email vorstand@mein-verein.example \
  --club "Mein Verein" --version 0.4.0 \
  --logo https://mein-verein.example/logo-weiss.svg \
  --logo-light https://mein-verein.example/logo-dunkel.svg \
  --primary '#117733' --dark '#0a2a14' --accent '#88ccaa' \
  --admin-first Vera --admin-last Vorstand

Ohne weitere Angaben fragt sudo bash install.sh alles Schritt für Schritt im Terminal ab und zeigt am Ende denselben Aufruf ohne Rückfragen zum Aufheben.

Was der Installer tut, jeweils nur, wenn es noch nicht so ist (ein zweiter Aufruf ist gefahrlos):

  1. Prüft System, Arbeitsspeicher und DNS.
  2. Installiert Docker aus dem offiziellen Repository und stellt die Log-Rotation ein.
  3. Richtet die Firewall ein: eingehend nur 22, 80 und 443.
  4. Schaltet automatische Sicherheitsupdates ein.
  5. Legt den Benutzer clubforge an, zieht das Image und entpackt die Betriebsdateien nach /opt/clubforge/deploy.
  6. Erzeugt die Einstellungen mit Zufalls-Geheimnissen (/opt/clubforge/deploy/.env) und einen Schlüssel für die Backups.
  7. Richtet das tägliche Backup ein (03:15 Uhr).
  8. Startet alles und prüft das Ergebnis. Der erste Start dauert einige Minuten, vor allem die Anmeldung und das Zertifikat.

Weitere Angaben, alle optional: --favicon, ein eigener Begriff für Gruppen (--group-one Team --group-other Teams --group-gender n), Mail (--smtp-host, --smtp-port, --smtp-user, --smtp-security, --smtp-from; das Passwort in der Umgebungsvariablen CF_SMTP_PASSWORD), ein selbst erzeugter Backup-Schlüssel (--age-recipient, siehe unten) und Speicher für Anhänge (--s3-*, siehe Danach). bash install.sh --help listet alle.

Die .env enthält alle Geheimnisse des Servers. Sie ist Teil jedes Backups; nie weitergeben, nie einchecken.

Oder: Hetzner Cloud mit OpenTofu

Statt die Schritte 2 bis 4 von Hand zu machen, legt eine OpenTofu-Vorlage bei Hetzner alles in einem Zug an: Server, Firewall (22, 80, 443), feste IPv4- und IPv6-Adresse und auf Wunsch die DNS-Einträge. Der Server installiert sich beim ersten Start selbst, mit Vereinsmarke und erster Admin-Person. Erprobt auf einem CAX11: von tofu apply bis zum grünen Check etwa 2,5 Minuten. Auf dem eigenen Rechner braucht ihr ein Terminal, einen SSH-Schlüssel (ssh-keygen -t ed25519), OpenTofu und Docker, um die Vorlage aus dem Image zu holen.

Konto, Projekt, API-Token

  1. Bei console.hetzner.cloud ein Konto anlegen und ein eigenes Projekt für clubforge erstellen. Object Storage für Backup-Kopien später am besten in einem zweiten Projekt.
  2. Im Projekt unter Sicherheit › API-Tokens ein Token mit Lesen und Schreiben anlegen. Es erscheint nur einmal.
  3. Den Vertrag zur Auftragsverarbeitung in der Konsole abschließen.
export TF_VAR_hcloud_token='…'     # nur im Terminal, nicht in eine Datei schreiben

Vorlage holen und ausfüllen

cid=$(docker create docker.io/cygnusbn/clubforge:0.4.0)
docker cp "$cid:/opt/clubforge/deploy/cloud" ./clubforge-cloud && docker rm "$cid"
cd clubforge-cloud/hetzner
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars

Ein ausgefülltes Beispiel:

app_host          = "app.mein-verein.example"
sync_host         = "sync.mein-verein.example"
login_host        = "login.mein-verein.example"
admin_email       = "vorstand@mein-verein.example"
club_name         = "Mein Verein"
ssh_public_key    = "ssh-ed25519 AAAA… name@rechner"
ssh_allowed_cidrs = ["203.0.113.7/32"]       # nur eure Adresse darf per SSH
clubforge_version = "0.4.0"
# server_type = "cax11"   location = "fsn1"   dns_zone = "mein-verein.example"
# age_recipient = "age1…"  (selbst erzeugter Backup-Schlüssel, siehe Schritt 5)

logo          = "https://mein-verein.example/logo-weiss.svg"
logo_light    = "https://mein-verein.example/logo-dunkel.svg"
color_primary = "#117733"
color_dark    = "#0a2a14"
color_accent  = "#88ccaa"
admin_first   = "Vera"
admin_last    = "Vorstand"

Ohne ssh_allowed_cidrs ist SSH aus dem ganzen Internet erreichbar. Standard ist ein CAX11 (arm64) in Falkenstein; server_type = "cx22" nimmt Intel, location auch nbg1 oder hel1. Optional: server_backups = true (Images des ganzen Servers von Hetzner, +20 %; ersetzt nicht das verschlüsselte Backup) und volume_size_gb für ein Zusatz-Volume.

Erst die feste IP, dann DNS

Damit die Namen beim ersten Start schon auflösen, entsteht die IP zuerst:

tofu init
tofu apply -target=hcloud_primary_ip.v4
tofu output ipv4

Die drei A-Einträge wie in Schritt 2 auf diese IP setzen und mit dig prüfen. Liegt die Domain in Hetzner DNS im selben Projekt, setzt ihr stattdessen dns_zone; dann legt der nächste Schritt die Einträge selbst an.

Server anlegen

tofu plan                                 # in Ruhe lesen: Server, Firewall, IPs
tofu apply
$(tofu output -raw installationsprotokoll)   # Fortschritt verfolgen

Der Server lädt install.sh von dieser Webseite, prüft die Prüfsumme, zieht das Image und richtet alles ein. Am Ende des Protokolls steht der Bericht von check.sh. Bricht die Installation wegen DNS ab: Einträge korrigieren und auf dem Server sudo /root/clubforge-install.sh erneut starten.

Zugangsdaten abholen

ssh root@<ipv4> cat /root/clubforge-erste-anmeldung.txt   # Einmalpasswort der ersten Admin-Person
ssh root@<ipv4> cat /root/clubforge-backup-key.txt        # ohne age_recipient: in den Passwortmanager
ssh root@<ipv4> rm /root/clubforge-erste-anmeldung.txt /root/clubforge-backup-key.txt

tofu output naechste_schritte fasst das zusammen. Weiter geht es mit Schritt 5 und Schritt 6. Ein späteres tofu apply baut den laufenden Server nicht neu; Einstellungen ändert ihr danach in der .env auf dem Server. tofu destroy entfernt Server, IPs, Firewall, Volume und DNS-Einträge der Vorlage, vorher die Backups sichern.

5. Backup-Schlüssel sichern

Backups werden verschlüsselt. Der Server kennt nur den öffentlichen Schlüssel; er kann Backups schreiben, aber nicht lesen. Den geheimen Schlüssel (AGE-SECRET-KEY-1…) braucht ihr, um ein Backup zurückzuspielen. Ohne ihn sind alle Backups wertlos.

  • Interaktiv zeigt der Installer ihn einmal an. In den Passwortmanager des Vereins (zwei Personen), erst dann mit ja bestätigen.
  • Ohne Rückfrage (--yes, cloud-init) liegt er in /root/clubforge-backup-key.txt: kopieren, in den Passwortmanager legen, Datei löschen. check.sh erinnert daran, solange sie da ist.
  • Am saubersten: selbst erzeugen und nur den öffentlichen Teil mitgeben. Dann entsteht auf dem Server keine Schlüsseldatei.
# auf dem eigenen Rechner
age-keygen -o schluessel.txt     # zeigt "Public key: age1…"; schluessel.txt in den Passwortmanager
sudo bash install.sh … --age-recipient age1…

6. Anmelden und prüfen

Mit --admin-first und --admin-last gibt es die erste Admin-Person schon. Ihr Einmalpasswort steht am Ende der Ausgabe, ohne Rückfrage in /root/clubforge-erste-anmeldung.txt (nach dem Weitergeben löschen). Ohne diese Angaben legt ihr sie jetzt an:

sudo -u clubforge /opt/clubforge/deploy/admin.sh vorstand@mein-verein.example Vera Vorstand
  1. https://app.mein-verein.example öffnen: Name, Farben und Logo des Vereins sind schon da.
  2. Mit E-Mail-Adresse und Einmalpasswort anmelden; die Anmeldung verlangt sofort ein neues Passwort.
  3. Die Person ist Vereins-Admin und richtet alles Weitere in der Web-App ein, unter Profil › Verwaltung: Gruppen, Funktionen, Begriffe, Marke, Verhaltensregeln, Datenschutz und Impressum, Mitgliederquelle (easyVerein oder CSV).

Den Zustand des Servers prüft jederzeit ein Befehl. Erwartet sind OK bei Diensten, DNS, Zertifikat, Endpunkten, Backup und Platte:

sudo -u clubforge /opt/clubforge/deploy/check.sh

7. Danach

Backups und Restore-Test

Das Backup läuft täglich, verschlüsselt, 30 Tage aufbewahrt, nach /var/backups/clubforge/. Ein Backup auf demselben Server schützt nicht vor dessen Verlust: Mit BACKUP_S3_* in der .env geht jedes zusätzlich in einen S3-Speicher, am besten in einem anderen Projekt als der Server. Einmal gleich nach der Installation und dann vierteljährlich zurückspielen, in einem Wegwerf-Container, ohne den Betrieb zu berühren:

cd /opt/clubforge/deploy
sudo -u clubforge ./backup.sh                      # sofort ein Backup
install -m 600 /dev/null /dev/shm/age-key.txt && nano /dev/shm/age-key.txt   # Schlüssel aus dem Passwortmanager
./restore.sh --identity /dev/shm/age-key.txt --verify
shred -u /dev/shm/age-key.txt

Erwartet ist „Restore-Test bestanden“ mit Zahlen für Mitglieder, Termine und Nachrichten.

Updates

Sicherheitsupdates des Systems laufen von allein; steht /var/run/reboot-required da, in einem ruhigen Moment neu starten. Neue clubforge-Versionen spielt ein Befehl ein: Backup, neues Image, Datenbank aktualisieren, Prüfung. Mit --announce sehen die Mitglieder die Wartung vorher in der App.

cd /opt/clubforge/deploy
sudo -u clubforge ./update.sh --version 0.4.0 --announce 10m

Hinweise zu jeder Version stehen unter Versionen.

Mail

Ohne SMTP-Zugang verschickt der Server keine Mails; App und Push funktionieren trotzdem. Die Werte CF_SMTP_HOST, CF_SMTP_PORT, CF_SMTP_USER, CF_SMTP_PASSWORD, CF_SMTP_SECURITY (starttls oder ssl) und CF_MAIL_FROM in die .env eintragen, dann docker compose up -d api worker in /opt/clubforge/deploy. Port 587 nehmen: Viele Cloud-Anbieter sperren Port 25 (teils auch 465), bei Hetzner sind beide für neue Konten gesperrt.

Anhänge (optional)

Für Fotos, Dateien und GPX-Strecken braucht es einen eigenen, privaten Bucket bei einem S3-Anbieter, z. B. Hetzner Object Storage, getrennt von den Backups. Ohne ihn läuft alles, nur ohne Anhänge.

# in /opt/clubforge/deploy/.env
CF_S3_ENDPOINT=https://fsn1.your-objectstorage.com
CF_S3_REGION=fsn1
CF_S3_BUCKET=mein-verein-anhaenge
CF_S3_ACCESS_KEY=…
CF_S3_SECRET_KEY=…
cd /opt/clubforge/deploy
docker compose up -d --force-recreate api worker
sudo -u clubforge ./check.sh                       # Abschnitt "Anhänge"

Karten (optional)

Die Kartenkacheln eurer Region liegen auf dem eigenen Server. Ein Befehl lädt sie und schaltet die Karten ein; --dry-run zeigt nur die Größe. Baden-Württemberg (bw) braucht etwa 1 GB, Deutschland (de) etwa 7,4 GB, mit Alpenraum (de-alpen) etwa 9,9 GB; mit --maxzoom 14 gut die Hälfte.

cd /opt/clubforge/deploy
./maps.sh --region bw --dry-run
./maps.sh --region bw

Suche nach Bedeutung (optional)

Die Suche findet dann auch Umschreibungen, etwa „Hauptversammlung“ die Mitgliederversammlung. Ein kleines Sprachmodell rechnet dafür auf dem eigenen Server, kein Text geht an Dritte. Der Befehl lädt das Modell (rund 130 MB) und schaltet den Dienst ein; beim Nachrechnen des Bestands braucht er rund 550 MB Arbeitsspeicher. Den Fortschritt zeigt check.sh, abschalten lässt sie sich unter Verwaltung › Suche.

cd /opt/clubforge/deploy
./embeddings.sh

Überwachung

Ein externer Dienst (Uptime Kuma, healthchecks.io o. ä.) ruft alle fünf Minuten https://app.mein-verein.example/api/v1/readyz auf und mailt bei Ausfall an zwei Personen. Mit BACKUP_HEARTBEAT_URL in der .env meldet jedes erfolgreiche Backup sich dort; bleibt die Meldung aus, gibt es Alarm.

8. Wenn es hakt

Erster Schritt immer check.sh; was rot ist, im Log des Dienstes ansehen: docker compose logs --tail=100 <dienst> in /opt/clubforge/deploy.

SymptomLösung
Installer meldet „DNS stimmt nicht“Einträge mit dig prüfen, warten, den Installer erneut starten; er setzt fort.
Zertifikatsfehler im BrowserPort 80 und 443 müssen auch in der Firewall des Anbieters offen sein (curl -I http://app.mein-verein.example muss 308 liefern). AAAA-Eintrag und Proxy prüfen. Nach vielen Fehlversuchen sperrt Let's Encrypt etwa eine Stunde.
Dienste werden beendet („Killed“)Weniger als 4 GB Arbeitsspeicher: größeren Server wählen.
„Image … nicht abrufbar“Version prüfen; mit --image ghcr.io/cygnusb/clubforge die andere Registry nehmen.
Anmeldung: „Kein aktives Mitglied mit dieser Adresse“admin.sh (bzw. admin.sh --member) mit derselben Adresse aufrufen.
Passwort vergessenIn der Verwaltung der Anmeldung (https://login.mein-verein.example/ui/console, Benutzer zitadel-admin, Passwort ZITADEL_ADMIN_PASSWORD aus der .env) ein neues setzen.

Weitere Wege führen zum selben Ergebnis: cloud-init (der Server richtet sich beim ersten Start selbst ein, bei jedem Anbieter) und OpenTofu-Vorlagen wie die für Hetzner auch für AWS und Google Cloud. Beide stecken im Image, unter /opt/clubforge/deploy/cloud/ und /opt/clubforge/deploy/cloud-init.yaml; auf den eigenen Rechner holt sie docker create docker.io/cygnusbn/clubforge:0.4.0 mit docker cp.
